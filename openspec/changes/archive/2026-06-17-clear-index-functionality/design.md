## Context

当前系统已有 `syncBlobsToIndex()` 功能，可以将 blobs/ 目录中的物理文件同步到 SQLite 索引中。索引数据存储在两个表中：
- `files` 表：存储文件元数据（hash、MIME type、标签、分类信息等）
- `classify_queue` 表：存储 AI 分类任务队列

用户希望能够清空这些索引数据，但保留 blobs/ 目录中的物理文件，然后重新同步建立新索引。

## Goals / Non-Goals

**Goals:**
- 提供清空 `files` 表和 `classify_queue` 表的功能
- 在 Options 页面提供"清空索引"按钮
- 提供二次确认，防止误操作
- 清空后不自动触发同步，让用户手动控制
- 保持与现有代码风格和架构一致

**Non-Goals:**
- 不删除 blobs/ 目录中的物理文件
- 不删除 thumbnails/ 目录中的缩略图
- 不清空配置数据
- 不添加自动同步功能
- 不修改现有 `syncBlobsToIndex()` 的行为

## Decisions

### Decision 1: 清空 `files` 表和 `classify_queue` 表

**选项考虑：**
- A. 只清空 `files` 表，保留 `classify_queue` 表
- B. 同时清空 `files` 表和 `classify_queue` 表 ✓
- C. 让用户选择清空哪些表

**选择 B 的理由：**
- 如果索引都清空了，分类队列也没有意义了
- 队列中的任务引用的 hash 在索引中不存在，会导致错误
- 简化用户体验，一个按钮完成所有清理
- 符合用户"完全重建索引"的预期

### Decision 2: 使用 SQL DELETE 而非 DROP TABLE

**选项考虑：**
- A. 使用 `DELETE FROM` 语句 ✓
- B. 使用 `DROP TABLE` + `CREATE TABLE`
- C. 删除整个 SQLite 数据库文件

**选择 A 的理由：**
- 更安全，保留表结构和索引
- 可以在事务中执行，保证原子性
- 不会破坏数据库 schema
- 实现更简单

### Decision 3: 清空后不自动同步

**选项考虑：**
- A. 清空后自动触发同步
- B. 清空后不自动同步，让用户手动点击 ✓
- C. 提供选项让用户选择

**选择 B 的理由：**
- 更可控，用户可以确认清空后再决定何时同步
- 避免误操作导致立即开始长时间的同步过程
- 与现有"同步"按钮的职责清晰分离
- 用户可能想要先检查或备份再同步

### Decision 4: 使用 Ant Design Popconfirm 组件

**选项考虑：**
- A. 使用 Ant Design Modal 对话框
- B. 使用 Ant Design Popconfirm 气泡确认框 ✓
- C. 使用浏览器原生 confirm()

**选择 B 的理由：**
- 与页面中"清空队列"按钮的实现一致（已经使用 Popconfirm）
- 更轻量，用户体验更好
- 符合现有 UI 风格

**确认文案：**
- Title: "清空索引"
- Description: "确定要清空所有索引吗？物理文件不会被删除，你可以随后重新同步。"
- OkText: "清空"
- CancelText: "取消"

## Risks / Trade-offs

| Risk | Likelihood | Impact | Mitigation |
|------|------------|--------|------------|
| 用户误操作清空索引 | 中 | 高 | 添加二次确认对话框 |
| 清空后忘记同步 | 低 | 中 | 清空后可显示提示，引导用户点击同步 |
| 性能影响（大索引） | 中 | 低 | SQLite DELETE 操作通常很快，且是后台操作 |
| 缩略图缓存未清理 | 低 | 低 | 缩略图会在下次访问时重新生成，可接受 |

## Migration Plan

1. 按照任务列表逐步实现功能
2. 测试验证清空和重新同步的完整流程
3. 无需数据库迁移（schema 不变）
4. 无需回滚计划（可以通过 git revert 轻松回退）
