## Context

当前 proxy 服务是一个 Express.js 服务器，用于接收和存储 Chrome 扩展捕获的媒体文件。服务启动后持续运行，代码变更需要手动重启。

**现状**：
- 服务通过 `node server.js` 启动
- 无文件监听机制
- 无调试日志系统
- 无调试端点

**约束**：
- 调试功能不应影响生产模式性能
- 热重启应保持服务可用性
- 与现有 Chrome 扩展 API 保持兼容

## Goals / Non-Goals

**Goals:**
- 实现调试模式启动命令，支持代码变更自动重启
- 实现分级调试日志系统
- 新增调试端点用于实时监控
- 保持生产模式零额外开销

**Non-Goals:**
- 不实现分布式热重启（单机服务）
- 不实现数据库持久化日志（内存日志即可）
- 不实现 WebSocket 实时推送（HTTP 端点足够）

## Decisions

### 1. 文件监听工具选择：nodemon

**选择 nodemon 的原因**：
- 简单配置，无需额外开发
- 广泛使用，生态成熟
- 支持 Express.js 专用配置
- 支持 delay 配置避免频繁重启

**备选方案**：
- `chokidar` + 自定义重启逻辑：更灵活但需更多开发
- `pm2`：功能过重，不适合开发模式

### 2. 日志系统设计：pino

**选择 pino 的原因**：
- 极高性能（比 winston 快 5x）
- 结构化 JSON 输出便于分析
- 支持分级日志（DEBUG/INFO/WARN/ERROR）
- 轻量级，调试模式才加载

**备选方案**：
- `winston`：功能丰富但性能较低
- `console.log` 增强：简单但缺乏结构化

### 3. 热重启策略：优雅关闭

**策略**：
1. 监听到文件变更
2. 发送 SIGTERM 给当前进程
3. 等待现有请求完成（最多 5s）
4. 启动新进程

**备选方案**：
- 直接 kill：可能导致请求中断
- 零停机重启：复杂度高，不适合开发模式

### 4. 调试端点设计：独立 `/debug` 前缀

**设计**：
- `/debug/status`：服务状态和配置
- `/debug/logs`：最近 N 条日志
- `/debug/restart`：手动触发重启

**安全考虑**：
- 仅在 DEBUG_MODE=true 时启用
- 不暴露敏感信息

## Risks / Trade-offs

| 风险 | 缓解措施 |
|------|----------|
| nodemon 延迟可能导致频繁重启 | 配置 delay: 1000ms 避免多次触发 |
| 调试日志可能暴露敏感数据 | 生产模式禁用 DEBUG_MODE |
| 内存日志可能占用过多 | 限制日志数量为 100 条 |
| 热重启可能丢失正在处理的请求 | 优雅关闭 + 请求超时配置 |

## Implementation Approach

### Phase 1: 调试模式启动
- 添加 nodemon 配置文件
- 修改 package.json 添加 dev 脚本
- 配置监听目录和延迟参数

### Phase 2: 调试日志系统
- 安装 pino 依赖
- 创建 logger 模块
- 在关键路径添加日志

### Phase 3: 调试端点
- 创建 debug 路由模块
- 实现状态、日志、重启端点
- 添加环境变量控制

### Phase 4: 集成测试
- 测试热重启流程
- 测试调试端点功能
- 验证生产模式无影响
